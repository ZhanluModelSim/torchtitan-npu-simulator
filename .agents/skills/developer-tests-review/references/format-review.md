# Test Format Review

本文件只审查测试文件的组织、收集、命名、可读性和隔离。它不判断生产功能是否覆盖，也不判断 CPU 数值或真实 NPU 训练是否正确。`review测试` 只静态读取；`更新测试` 可以在修改后执行适用的收集、lint 或 testcase，但不能用执行结果替代本文件的代码审查。

## Workflow

### 1. 固定格式依据

按 Rules 1 的顺序读取仓库规则、测试配置、相邻测试和固定上游约定，记录发生冲突时采用的具体依据。不要把全仓历史写法的多数票当成标准。

### 2. 确认文件和入口

确定修改文件属于 CPU UT、NPU integration testcase、golden/asset、fixture、runner 还是 CI 配置。沿正常 pytest 或 integration runner 入口静态追踪文件是否会被包含；无法确定的动态条件如实记录为“静态无法确定”。

### 3. 重写测试行为

把每条测试按实际代码逻辑重写为“给定实际条件，调用实际生产动作，直接断言主要结果”。先检查这个句子能否准确概括测试；若同一测试包含不同准备、不同调用和不同最终结果，记录为结构问题并考虑拆分。

### 4. 按 Rules 执行格式审查

逐条应用文件位置、pytest/runner 收集、命名、结构、辅助对象、注释和状态隔离规则。规则只记录静态可见事实；不要为了证明格式问题而执行测试或猜测动态运行状态。

### 5. 输出格式结论

每个问题写准确文件和测试节点、静态事实以及最小修改。格式问题单独输出，不能改写为正向功能未覆盖；没有问题时写明已读取的依据和入口。

## Rules

### 1. 依据顺序

优先使用 PR 版本中的 `pyproject.toml`、pre-commit、测试入口和 `.agents` 规则；其次使用被修改的同一测试文件；再次使用同一生产模块的相邻测试；然后使用当前固定 TorchTitan 版本中的同模块测试；最后才使用 pytest 和 Python 的公开约定。发生冲突时使用更靠前且更具体的依据，并在报告中写出对照文件。

### 2. 文件位置

#### 2.1 CPU UT 路径

CPU UT 使用当前仓库的 `tests/unit_tests` 作为根目录，目录层级参考其中的测试布局；测试必须按当前仓库
的正式生产代码目录一一对应组织。对
`torchtitan_npu/<area>/<module>` 下的行为，优先放在
`tests/unit_tests/<area>/<module>/test_*.py`；例如模型、算子、override、patch 和
compile 测试分别进入对应的 `models/`、`ops/`、`override/`、`patches/` 和
`compile/` 子目录。

#### 2.2 Integration testcase 路径

真实 NPU 集成 testcase 放在 `tests/integration_tests` 的现有模型定义和 runner 结构中。模型 case 应由对应 `build_*_test_list` 注册，不能只在独立脚本中声明一个不会被 suite 选择的 case。跨模型的 runner 逻辑回到 runner，模型和 override 组合回到对应模型定义。

#### 2.3 Golden 和 asset 路径

golden、固定输入和数据 asset 放在仓库已有的 `tests/assets` 或 integration 测试约定目录中。golden 文件名必须能稳定映射到 testcase；不要把一次运行输出、PR 编号或临时目录当作长期测试路径。

#### 2.4 辅助文件

辅助模块不能使用会被 pytest 当成测试的文件名，不能通过改变文件名逃避或伪造收集。公共 fixture 只有在多个测试共享同一稳定准备过程时才放入公共位置。

### 3. Pytest 和 integration runner 收集

#### 3.1 Pytest 收集

文件、类、函数和参数化测试必须符合仓库的 pytest 配置。pytest 测试类不定义 `__init__`；每条测试必须能由文件、类、函数和稳定参数定位。

#### 3.2 参数化标识

参数化测试不能依赖 `case0`、对象地址或长元组作为唯一名称。参数含义会影响定位时，提供简短稳定的 `ids=`，并让 id 能区分模型、配置或主要结果。

#### 3.3 Integration suite 收集

integration testcase 必须经过 `run_tests.py` 的 suite 注册和正常入口选择，并具有稳定的 `test_name`。`disabled`、排除参数、NPU 数量过滤和 CI suite 选择都要在静态报告中说明；只存在于 README 或未注册列表中的 case 不算入口包含。

### 4. 测试命名

#### 4.1 名称与行为一致

顶层函数优先使用 `test_<对象或动作>_<条件或预期结果>`；名称包含能区分相邻测试的条件和一个主要结果，不必罗列所有辅助断言。

#### 4.2 避免空泛词

避免单独使用 `basic`、`normal`、`success`、`case1`、`unaffected` 或 `regression` 等离开正文无法定位的词。类已经表达对象时，方法名不重复类名。

#### 4.3 名称层级准确

名称声称端到端、真实 tokenizer、真实 NPU、loss golden 或数值等价时，测试代码必须处于相应层级并包含对应检查。名称和代码不一致只记录命名问题；是否覆盖生产功能由 UT/ST 规则判断。

#### 4.4 一个名称对应一个结果

一条测试应能用一个稳定名称概括。若测试有不同准备、不同生产调用和不同最终结果，拆成多条测试或明确说明它们共同保护的单一结果。

### 5. 准备、调用和断言结构

#### 5.1 准备与调用分开

导入默认置顶；准备、真实调用和断言之间用空行分开。只有可选依赖、循环依赖或明确导入顺序要求才使用局部导入。

#### 5.2 断言靠近结果

断言应靠近产生被测结果的调用，并直接表达主要结果。辅助函数包含断言时，名称或说明必须写清它同时检查的结果；不能把关键断言藏在一个名为 `run_case` 或 `check_all` 的泛化 helper 中。

#### 5.3 最小辅助函数

多条测试重复准备过程时可以复用最小 fixture 或辅助函数，但不能为了复用改变输入表示、绕过真实生产入口或合并互不相干的结果。

### 6. Fake、Stub、Spy 和 fixture

Fake 表示隔离后的可运行替身，Stub 表示固定返回，Spy 表示记录调用。名称不能把模拟对象冒充真实生产对象；模拟 tokenizer、数据集、模型、算子或 process group 时，fixture 说明必须写清支持的输入范围和未覆盖的真实边界。

### 7. 注释和文档结构

注释只解释代码不能直接表达的 shape、边界、fixture 编码、导入顺序或平台限制。模块说明只写文件职责和共享输入表示，不枚举全部测试，不写审查结论。测试函数说明若只是重复名称则删除；真正的限制应说明原因和适用范围。

### 8. 状态和外部依赖

#### 8.1 RNG 和环境

随机输入使用局部 generator 或可恢复的 RNG 范围。环境变量、debug 开关和全局配置必须在 fixture 结束时恢复。

#### 8.2 patch、registry 和 import cache

registry、monkeypatch、单例、钩子、process group、`sys.modules` 和 import cache 的修改必须可靠恢复。静态可见恢复缺口时记录为“隔离风险”，不运行测试猜测它是否污染后续测试。

#### 8.3 文件和进程

临时文件使用测试独占目录，子进程输出使用独占路径。测试不得依赖另一条测试先执行，也不得依赖未声明的网络、设备或外部初始化。

### 9. 格式审查边界

格式问题只描述文件、收集、命名、结构、可读性和隔离事实。它不能直接判定正向功能未覆盖、ST 缺失、数值错误或生产代码错误；这些结论必须转到 `ut-review.md` 或 `st-review.md`。

## 输出

| 位置 | 类型 | 静态事实 | 最小修改 |
| --- | --- | --- | --- |

类型只使用“文件位置 / pytest 收集 / integration runner 收集 / 命名 / 测试结构 / 辅助对象 / 注释 / 状态隔离 / 测试入口”。旧测试中的高风险写法及迁移动作记录在本地迁移指导中，不随本技能发布，也不在本文件重复。
