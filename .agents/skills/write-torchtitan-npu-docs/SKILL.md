# torchtitan-npu 文档写作

从读者要完成的任务出发，写清 NPU 适配的动机、激活方式、行为边界和验证依据。保持内容克制，不用文案掩盖实现状态或硬件限制。

## 读取上下文

1. 从仓库根目录开始，完整读取目标文档路径上适用的 `AGENTS.md`；如果上级目录存在更近的同名文件，也一并读取。
2. 读取目标文档及相邻文档，确认既有结构、术语和链接方式。
3. 读取与结论直接相关的源码、配置、测试和脚本。用 `rg` 定位注册名、导入路径、环境变量、限制注释和测试入口。
4. 读取 [references/project-writing-contract.md](references/project-writing-contract.md)，应用项目专属的信息结构和术语规则。
5. 撰写仓库首页、操作指南或执行文档审阅时，再读取 [references/document-validation.md](references/document-validation.md)，应用文档验证状态和检查清单。

## 工作流

### 1. 确定文档任务

从请求和仓库上下文确定以下信息：

- 文档类型：仓库首页、功能说明、架构说明、操作指南、数值报告或设计计划（包括RFC）。
- 目标读者：torchtitan-npu 使用者、本仓开发者、NPU 算子开发者或精度验收人员。
- 阅读结果：完成配置、理解边界、复现实验、审阅设计或定位问题。
- 范围：明确包含内容和边界；只有当范围容易混淆时再写非目标，并注明需要链接到其他文档的细节。

只有缺少的信息会实质改变文档范围或技术结论时才请求确认；其余信息从仓库证据中确定。

### 2. 建立事实清单

为关键结论找到直接依据，并区分：

- `已实现`：存在对应代码路径。
- `已验证`：存在测试、日志或可复现命令支持。
- `有限支持`：实现带设备、版本、shape、dtype、并行方式或序列布局限制。
- `未验证`：缺少足够的测试、日志或可复现命令，不能确认支持范围。
- `计划中`：只出现在计划、TODO 或未合入方案中。

发现 `AGENTS.md`、现有文档与源码不一致时，记录差异，按直接证据修正文档或标注待确认，不要静默拼成一个结论。

同时记录文档的上游真源和可能受影响的下游文档。实现、配置或测试是当前行为的真源；设计文档和功能说明解释这些事实；README 和操作指南只提炼使用者需要的部分。不要让下游摘要反向定义实现状态。

### 3. 选择结构并起草

- 首段直接回答「项目或功能是什么、为什么存在、何时使用」。
- 先写使用者需要的激活方式和限制，再展开内部实现。
- 当文档同时涉及多类能力时，将兼容性修复、性能或内存快路径、数值 golden 实现和后端算子 patch 分开描述。
- 主题涉及互斥 override、导入副作用、NPU 环境要求或分布式 tensor 语义时，给出显式提示。
- 只有支持情况随设备、runtime、dtype、layout、并行方式或激活模块变化且需要比较时，使用支持矩阵；每个单元格都要有源码、测试或实验依据。
- 只在关系复杂时使用表格、流程图或目录树；不要展示与主题无关的完整文件清单。

### 4. 校对中文与技术表达

#### 语气与结构

- 准确、清晰、可执行优先于修辞；先写结论、适用条件和限制，再补背景。
- 使用克制的说明语气，不使用第二人称、问候语、感叹号、宣传口号或空泛形容词。
- 避免「赋能」「抓手」「闭环」「沉淀」「拉通」「打通」「兜底」等黑话；只有具备严格技术定义时才保留并在首次出现处解释。
- 一个段落只承载一个主要信息点；拆分欧化长句，保持并列列表的句式和信息密度一致。
- 使用能表达用途的标题，删除标题、首段和列表之间的重复内容。

#### 排版与标识符

- 中文正文使用全角标点和直角引号 `「」`，不使用中文双引号 `“”`。
- 在中文与英文缩写、可读英文单词、独立数字或版本号之间保留空格，例如「NPU 训练」「版本 2.0」。
- 不改写或机械加空格到行内代码、代码块、模块路径、配置键、环境变量、JSON 键、URL、API 路径、数据库字段及其他机器可读标识符。
- 保留产品和技术名称的官方大小写；正文中统一使用 `ID`、`HTTP`、`URL`、`JSON`、`API`、`AI`、`LLM`、`Python`、`GitHub`、`YAML` 和 `gRPC` 等标准形式。

#### 术语与数值

- 按 [references/project-writing-contract.md](references/project-writing-contract.md) 统一项目术语；同一概念不混用中文别名、缩写和包名。
- 按语义翻译状态词，符合中文表达习惯，不机械直译：`Success` 可写「已完成」，`Invalid` 可写「格式有误」或「校验未通过」，`Not Found` 应说明未找到的具体对象。
- 写明数值的对象、单位、版本和测量条件；区分「提高 5 个百分点」与「相对提高 5%」，避免「缩小 3 倍」「大约 3 点左右」等歧义。
- 优先使用「阈值、部署、配置、启用、返回、回溯、标识、截至」等规范写法，检查常见错字。
- 不声称未经测量的性能收益，不把单卡结果推广为分布式结论。
- 命令应可复制执行。

### 5. 验证交付

1. 按正确性、易理解性和规范性检查文档。核对文件路径、目录结构、能力清单、模块导入、override 注册名、配置字段、版本、支持范围和相对链接。
2. 从目标文档中提取已有命令；新写命令时，从相关源码、配置、脚本或测试中提取依据。环境满足且命令安全、成本可控时执行；环境缺失、用户要求跳过或命令成本过高时保留静态检查，并按 `passed`、`failed`、`skipped`、`not-run` 记录状态和原因。
3. 运行与改动最相关的轻量检查；不要仅为校对文档触发昂贵的 NPU 训练，也不要用另一条替代命令冒充文档命令已经通过。
4. 检查标题层级、代码块语言和计划/现状标记。
5. 交付时列出修改的文档、事实依据、验证状态（含命令或静态证据）和未确认原因；说明仍需 NPU 环境确认的内容。

## 编辑边界

- 只修改请求范围内的文档；需要同步的下游文档先报告，发现实现问题时先报告，不顺带扩大修改范围或改训练代码。
- 不为填满模板添加无关章节，不重复源码可以直接表达的细节。
- 仅在主题相关时说明硬件、runtime、checkpoint、shape、dtype 或并行限制。
- 不扩展解释未请求的历史代码；操作指南和使用说明按当前实现说明激活方式、命令和限制。
- 请求主体是代码实现、训练排查或项目分析时，使用对应技能，不以文档说明代替实现或诊断。
- 不用「领先」「强大」「赋能」等宣传词，也不直接称呼读者。
