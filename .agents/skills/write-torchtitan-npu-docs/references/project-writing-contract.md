## 证据优先级

按以下顺序确认事实：

1. 当前用户请求与适用的 `AGENTS.md` 中的明确约束。
2. 当前源码、配置、测试和脚本。
3. 与实现同步维护的现有文档。
4. 本地相邻的上游 torchtitan checkout。
5. 计划文档、历史说明和外部材料。

适用的 `AGENTS.md` 描述项目意图和边界，源码描述当前实现。二者冲突时应指出差异；不要仅凭旧文档断言当前行为，也不要用计划文档证明功能已经完成。

对每个重要结论，至少保留一个可定位的依据，例如源码符号、配置字段、测试名、命令输出或带环境信息的实验结果。

## 文档来源与同步关系

按以下关系组织文档，不让摘要或计划反向定义当前实现：

```text
AGENTS.md + 源码 + 配置 + 测试 + 脚本
                    │
                    ├──> 架构说明与功能文档 ──> README 导航
                    │                         └──> 操作指南
                    └──> 模块契约与限制说明 ──> 支持矩阵

计划、RFC ──[实现并取得验证证据后]──> 当前状态文档
```

- 修改实现、配置或测试后，检查相关架构说明、功能文档、README 和操作指南是否需要同步。
- 修改架构说明或功能文档时，核对其上游实现证据，并检查下游摘要是否仍然一致。
- README 只保留定位、快速开始、支持范围、结构入口和文档入口，不复制详细设计。
- 操作指南从实际脚本、配置和可运行命令派生，不从另一个操作指南转述。
- 计划文档只描述建议和未完成工作；功能合入且取得证据后，才迁移到当前状态文档。
- 默认使用 Git 历史记录文档变更。只有现有文档体系明确要求修订表时才增加，不为套用模板创建维护负担。

## 项目叙事

将 `torchtitan-npu` 描述为 torchtitan 的 Ascend NPU 适配层。重点说明它如何使用 torchtitan 的公开扩展点和 `patches/` 的受控副作用机制，不要写成独立训练框架或 torchtitan fork。

区分两类扩展边界：

- torchtitan 组件替换：使用配置级 `@override`，通过 `config.override.imports` 显式激活。
- 依赖补丁：在 `patches/` 中为 `torch`、`torch_npu` 或其他依赖注册或替换实现，包导入时产生受控副作用。

解释组件时，按真实动机归类：

- 兼容性：绕开 NPU 不支持或行为不一致的上游路径。
- 性能或内存：使用融合算子、设备专属实现或 swap memory。
- 数值 golden：用 PyTorch 单算子实现复现指定基线，服务于精度定位和验收。
- 模型专属：只适用于指定模型或配置，不写成通用能力。

## 必须写明的边界

主题涉及相关能力时，主动核对并说明：

- override 是否需要显式导入，以及准确的模块路径。
- 多个 override 是否 claim 同一配置节点，能否同时启用。
- 导入 `torchtitan_npu` 会注册哪些 backend patch。
- 是否要求 `torch_npu`、CANN、HCCL 和可用的 Ascend NPU 环境。
- 限制是否与设备代际、runtime 版本、dtype、shape、序列布局或 broadcast 方式有关。
- 是否同时支持本地 tensor 与 `DTensor`，以及 mesh、placements、shape、stride 是否保持。
- checkpoint、host-offload 或 swap tensor 是否有序列化限制。
- 结论来自 CPU 单测、NPU 单卡、分布式训练还是静态源码检查。

不要把「有实现」写成「所有配置均支持」，也不要把「测试覆盖」写成「生产环境已验证」。

## 支持矩阵

当支持情况随设备、runtime、dtype、layout、并行方式或激活模块变化时，使用紧凑矩阵代替散落说明。按主题选择必要列，不要求每张表使用全部字段。

| 能力 | 激活方式 | 环境 | 数据约束 | 验证范围 | 状态 |
|------|----------|------|----------|----------|------|
| `<能力名>` | `<模块或配置>` | `<设备/runtime>` | `<dtype/shape/layout>` | `<测试或实验>` | `<已验证/有限支持/未验证/计划中>` |

- 每行只描述一个可独立判断的能力。
- 从源码、测试或实验记录填写，不依据相邻项目或上游默认行为推断。
- 差异只写一次；矩阵后补充无法压缩成单元格的限制。
- 未验证的组合留空或明确标为「未验证」，不要用模糊的「支持」覆盖。

## 项目术语

通用中文校对规则见主 `SKILL.md`。本节只记录项目专属约定：

- 首次出现不常见缩写时给出全称或一句定义；目标读者熟悉的 torchtitan、NPU、CANN 等名称无需反复解释。
- 使用 `torchtitan`、`PyTorch`、`torch-npu`、`Ascend NPU`、`CANN`、`HCCL`、`DTensor`、`MoE`、`RoPE`、`RMSNorm` 和 `DeepSeek-V4` 的标准拼写。
- `DSV4` 可在首次写为「DeepSeek-V4（DSV4）」后继续使用。
- `golden` 指数值基线时可保留英文，并在首次出现时说明基线来源。
- `override`、`patch` 和 `dispatcher` 在代码机制语境中可保留英文，不进行生硬直译。
- 「数值对齐」是本仓固定技术术语，不按通用黑话规则替换；使用时写清对齐对象、指标、阈值和环境。

## 文档类型

### 仓库首页

推荐顺序可参考当前 README 的信息流，但不要机械套用现有章节名：

1. 一句话定位与适用边界。
2. 与 torchtitan、torch-npu 的关系和接入方式。
3. 环境与安装要求。
4. 最小可运行或最小激活示例。
5. 特性支持概览、项目结构和文档入口。
6. 必要时增加支持矩阵。
7. 已知限制和开发验证命令。

首页用于导航，不展开长篇算法推导，也不机械复刻当前 README 的所有附加板块。

### Override 或 patch 说明

至少回答：

1. 解决什么兼容性、性能、内存或数值问题。
2. 替换或补齐哪个上游组件、配置节点或 ATen backend。
3. 如何注册和激活，是否存在导入副作用。
4. 配置如何迁移。
5. 输入输出、`DTensor` 和分布式语义是否变化。
6. 与其他 override 的冲突、硬件限制和测试依据。

### 架构或设计说明

先写目标和职责边界，再写组件关系、控制流程和取舍。明确哪些修改属于上游 torchtitan，哪些属于本仓 backend 层。尚未实现的内容或者过往状态不需要说明。

仅当三个以上组件或状态转换难以用短段落说明时使用 Mermaid 图。图后补充关键限制，不能让图替代精确的模块路径和配置说明。

非目标不是固定章节；只有当范围容易与相邻文档混淆时，才单列说明。

### 特性文档

回答「特性解决什么问题、适用于什么范围、如何启用、有哪些限制」。推荐按以下顺序组织：

1. 一句话定位与适用边界。
2. 适用模型、设备/runtime、依赖和默认状态。
3. 实现原理或组件关系，只解释影响使用和维护的部分。
4. 配置或激活方式，给出可复制示例和源码路径。
5. 支持范围、互斥关系和已知限制。
6. 验证依据、结果和相关链接。

- 将兼容性、性能、内存和数值 golden 路径分开，区分默认启用与按需启用。
- 多个环境或配置存在差异时，使用紧凑支持矩阵；每行对应一个可独立判断的能力。
- 不把源码路径或配置存在写成用户可用；缺少证据的组合标为「未验证」。

### 开发者指南

回答「开发者需要理解哪些边界、按什么流程修改和验证」。推荐按以下顺序组织：

1. 目标、读者、前置条件和边界。
2. 目录或组件职责，以及可使用的扩展点。
3. 修改、注册、配置或排查流程。
4. 测试、Lint 或其他验证入口，说明命令、环境和成本。
5. 预期结果、常见失败和提交前自查。

- 以源码、配置和测试为真源，保留准确的路径、符号和配置键。
- 涉及测试分层或命令选择时，使用表格或决策列表，区分 CPU 单测、NPU 冒烟和分布式验证。
- 说明关键取舍和原因，不把用户安装步骤或内部实现细节混入同一流程。

### 用户指南

回答「如何完成一个具体任务」。推荐按「前置条件 → 输入或权重准备 → 配置与命令 → 预期结果 → 判读 → 常见失败或清理」组织：

- 在开头集中说明版本配套、必需依赖、设备要求和工作目录，并区分必需项与可选项。
- 命令应可复制执行，写明默认值、路径、环境变量和输入格式；参数较多时使用紧凑表格。
- 将硬件、runtime、checkpoint、磁盘空间和不可逆操作等限制放在对应步骤附近。
- 使用编号列表描述操作顺序，使用提示块说明风险；内部原理链接到特性文档或开发者指南，不在用户指南中重复展开。

以上结构按文档复杂度裁剪，简单文档不强行补齐所有小节。

### RFC

RFC 用于记录尚未完成的设计提案、取舍和评审决议，不把提案内容写成已实现状态。通常以标题、概述、主体和评审记录组织，不单设元数据块。可参考 Issue #93，按以下顺序组织：

1. **概述**：用一段话说明问题、提案和预期结果；随后用要点列出核心思路。
2. **动机与现状**：说明当前路径、具体问题和直接证据。多个方案或路径存在差异时，使用对比表，并给出上游机制或历史决策作为背景。
3. **目标与边界**：分别列出要解决的问题和明确不处理的范围；只有在范围容易混淆时再单列非目标，避免把实现细节写成目标。
4. **核心设计**：说明组件职责、目录归属、激活入口、控制流程和新增功能的决策路径。三个以上组件或状态转换难以用短段落表达时，再使用目录树、流程图或关系表。
5. **约束与兼容性**：记录上游接口限制、硬件和 runtime 要求、配置冲突、checkpoint 互操作、并行语义及临时 patch 的退出条件。
6. **迁移与特性映射**：说明现状到目标状态的迁移原则、阶段、回滚边界，并用表格映射特性、承载目录、激活方式、优先级和依赖关系。
7. **验证与验收**：按实现层次说明验证方法；涉及数值时记录基线、指标、阈值、设备、版本、随机性和样本范围，区分比特一致、数值近似和冒烟看护。
8. **评审记录与未决问题**：记录评审日期、结论、行动项、负责人或关联 Issue；未决事项明确当前决策和后续触发条件。
9. **参考**：列出源码、测试、上游 Issue/PR、设计文档和外部 API 文档链接。

- 每个重要设计结论都要有可定位的依据；无法确认的内容标为「待确认」或「计划中」。
- 用「当前状态」「提案状态」「已验证」区分现状、设计和证据，避免 RFC 与功能文档互相定义实现状态。
- RFC 只保留影响设计决策的实现细节；可独立复用的命令和使用步骤链接到特性文档、开发者指南或用户指南。

## 交付检查

- 首段是否直接说明用途和边界。
- 实现、验证、有限支持和计划是否分开。
- 当前文档是否能追溯到上游真源，下游摘要是否需要同步。
- 激活模块、互斥关系与导入副作用是否准确。
- 支持矩阵是否与代码、测试和实验范围一致。
- 硬件与分布式假设是否靠近相关说明。
- 命令、相对链接和代码示例是否可用。
- 是否删去重复、宣传性或无法验证的句子。
- 是否保留机器可读标识符的原始拼写。
